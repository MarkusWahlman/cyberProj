Note: The flaws are categorized according to the 2025 OWASP Top 10 list (https://owasp.org/Top10/2025/).

FLAW 1 (A07:2025 Authentication Failures):
Flaw with fix: https://github.com/MarkusWahlman/cyberProj/blob/main/backend/src/routes/authRoutes.ts#L31

The login route is not rate limited, giving an attacker the ability to make unlimited requests to brute-force password combinations or use leaked credential lists. 

This can be fixed by implementing a rate limiter that targets the specific account being brute-forced. Using a custom key generator that limits requests based on the username provided in the request body (falling back to IP) defeats botnets, as the account itself will reject attempts after 5 failures in a 15-minute window, regardless of how many IPs the attacker uses.

In screenshot `flaw-1-before-1.png`, the `brute-force.js` script successfully sends requests without being blocked. In `flaw-1-after-1.png`, the server correctly returns a 429 Too Many Requests status code after the 5th attempt.

FLAW 2 (A01:2025 Broken Access Control):
Flaw with fix: https://github.com/MarkusWahlman/cyberProj/blob/main/backend/src/routes/authRoutes.ts#L39

The application has a Broken Access Control vulnerability because the endpoint for retrieving users fails to properly enforce administrative privileges. While it checks if a user is authenticated, it lacks authorization validation, allowing standard users to access sensitive personal data of all registered users.

This can be fixed by applying an authorization middleware to the route that verifies the authenticated user's role is set to admin. If a non-administrative user attempts access, the server will immediately reject the request with a forbidden status code.

In screenshot `flaw-2-before-1.png`, a standard user accesses the admin page and all users are successfully listed. In `flaw-2-after-1.png`, the same request is blocked with a 403 Forbidden status code.

FLAW 3 (A04:2025 Cryptographic Failures):
Flaw with fix: https://github.com/MarkusWahlman/cyberProj/blob/main/backend/src/services/authService.ts#L54

The application relies on an insecure and predictable token generation mechanism for password resets. Because the token is generated by hashing the current timestamp with a weak algorithm, simultaneous reset requests for two different users will result in the exact same token being issued, compromising the authentication flow.

This can be fixed by replacing the vulnerable logic with a secure random number generator. Using built-in cryptographic libraries to generate long hexadecimal strings ensures that all tokens are unpredictable.

In screenshot `flaw-3-before-1.png`, the generated password reset tokens for the users "admin" and "test" are identical because they were requested simultaneously. In `flaw-3-after-1.png`, the generated tokens for "admin" and "test" are unique.

FLAW 4 (A05:2025 Injection):
Flaw with fix: https://github.com/MarkusWahlman/cyberProj/blob/main/backend/src/repositories/userRepository.ts#L31

The application contains a critical SQL Injection vulnerability within the user search functionality. The issue exists because the code concatenates untrusted user input directly into database queries, rather than using secure methods to handle the data. If an attacker submits a crafted payload containing SQL control characters, they can manipulate the structure of the underlying database query to bypass authentication, read arbitrary data, or modify database records.

This can be fixed by using parameterized queries or other safe methods. Rewriting the query to safely bind the parameters ensures the database engine treats the user input as a literal rather than executable code.

In screenshot `flaw-4-before-1.png`, a malicious SQL payload is submitted that successfully escapes the search query and injects a fake admin user into the results. In `flaw-4-after-1.png`, the same malicious payload is safely treated as a literal search string, resulting in no fake users being returned.

FLAW 5 (CSRF Flaw):
Flaw with fix: https://github.com/MarkusWahlman/cyberProj/blob/main/backend/src/routes/authRoutes.ts#L54

The application has a critical Cross-Site Request Forgery (CSRF) vulnerability because a sensitive action (account deletion) is exposed via an HTTP GET request. By design, GET requests should only be used to retrieve data and never to modify server state. While modern browsers default to `SameSite=Lax` cookies (which prevents cross-origin background requests like image tags from sending cookies), they still attach cookies during cross-origin navigations. An attacker can exploit this by embedding a JavaScript redirect on a webpage. When an authenticated victim visits the malicious page, their browser automatically performs a navigation to the deletion URL, attaches the session cookie, and executes the account deletion without the user's consent. 

This can be fixed in two steps. First, the route must be changed to only accept POST requests instead of GET requests. Second, CSRF protection must be added either by including a unique, hidden token in the form or by checking for a specific custom header (like `X-Requested-With`). This works because modern browsers prevent external, malicious websites from adding custom headers to their requests. By checking for this header, the server can guarantee the request came from the real frontend and block any forged attacks.

In screenshot `flaw-5-before-1.png`, the user clicks on a link. As seen in `flaw-5-before-2.png`, the page's JavaScript automatically redirects the user directly to `/delete-account`, which immediately deletes the account since it is a simple GET request. In `flaw-5-after-1.png`, attempting to navigate to the `/delete-account` URL does nothing, because the route now safely requires a POST request with the correct custom header.
